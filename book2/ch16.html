Tool CallingTool Calling

Haron can't check an order, convert a currency or send an email. It has no hands. What it can do is write a precise request: "please run get_order with ORD-100232." Your code runs it and hands back the result. This is tool calling (also called function calling), and it's the bridge from a model that talks to an app that does things.

Haron order check nahi kar sakta, currency convert nahi kar sakta, email nahi bhej sakta. Uske haath nahi. Woh jo kar sakta hai: sateek request likhna: "kripya ORD-100232 ke saath get_order chalao." Aapka code use chalaata hai aur result wapas deta hai. Ise tool calling (ya function calling) kehte hain, aur yeh baat karne wale model se kaam karne wali app tak ka pul hai.

The round tripAana-jaana

RememberYaad rakho

The model never runs anything. It only asks. Your code decides whether to run the tool, checks the arguments, runs it, and sends back the result (or an error). That's where all your control and safety lives.

Model kabhi kuch nahi chalaata. Woh sirf maangta hai. Aapka code tay karta hai tool chalaana hai ya nahi, arguments check karta hai, chalaata hai, aur result (ya error) wapas bhejta hai. Aapka saara control aur suraksha wahin hai.

Good tools vs confusing toolsAchhe tools vs uljhe tools

AI behaviour

Models invent tools and argumentsModels tools aur arguments bana lete hain

A model may call lookup_order when your tool is get_order, pass "100232" without the prefix, or add a field you never defined. Validate every call against the schema and send back a clear error ("Unknown tool. Available: get_order, convert_inr"): models usually correct themselves on the next step. Book 2, Chapter 7 has a full validating tool registry.

Model get_order ki jagah lookup_order call kar sakta hai, prefix ke bina "100232" de sakta hai, ya aisa field jod sakta hai jo aapne banaaya hi nahi. Har call ko schema se validate karo aur saaf error wapas bhejo ("Unknown tool. Available: get_order, convert_inr"): models aksar agle step mein khud sudhaar lete hain. Book 2 ke Chapter 7 mein poori validating tool registry hai.

Engineer's note

Parallel calls and errorsParallel calls aur errors

Models can ask for several tools at once (look up three orders in one step). Run them concurrently and return all results together in one message. If a tool fails, return the failure as the result (with is_error); never just drop it, or the model will wait for a result that never comes or assume success.

Models ek saath kai tools maang sakte hain (ek step mein teen orders dekho). Unhe saath-saath chalao aur saare results ek message mein lautao. Agar tool fail ho, failure ko result ki tarah lautao (is_error ke saath); kabhi bas chhod mat do, warna model kabhi na aane wale result ka intezaar karega ya safalta maan lega.

In the real world

Read tools and write toolsRead tools aur write tools

Label every tool by risk. Read tools (look up an order) can run freely. Write tools (issue a refund, send an email) need limits and idempotency keys so a retry doesn't refund twice. Dangerous tools (delete an account, move money) need a human to approve. This one habit prevents most agent disasters.

Har tool ko risk se label karo. Read tools (order dekhna) aazaadi se chal sakte hain. Write tools (refund dena, email bhejna) ko limits aur idempotency keys chahiye taaki retry do baar refund na kare. Dangerous tools (account delete, paisa bhejna) ko insaan ka approval chahiye. Yeh ek aadat zyaadatar agent haadson ko rokti hai.

What we learnedHumne kya seekha

  1. I ask for tools; your code runs them.
  2. I can chain tools: one result feeds the next request.
  3. Clear names, descriptions and strict schemas make me use tools well.
  4. Validate everything, return errors as results, and gate risky tools.
  1. Main tools maangta hoon; aapka code chalaata hai.
  2. Main tools jod sakta hoon: ek result agli request ko khilaata hai.
  3. Saaf naam, descriptions aur sakht schemas se main tools achhe se use karta hoon.
  4. Sab validate karo, errors result ki tarah lautao, aur risky tools par pehra lagao.
