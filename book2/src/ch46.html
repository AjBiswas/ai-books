When Asha asks Haron to book a flight, who is actually calling the airline's API? Not Asha: she's asleep. Not a random program: it must prove what it is. Agents are a new kind of user, a non-human identity, and they act on behalf of humans. Giving an agent your password, or a forever API key with every permission, is how prompt injection (Ch 27) turns into real damage. This chapter shows the pattern that contains it: every agent gets its own identity, and every action carries a short-lived token saying who, for whom, what and until when.

Jab Asha Haron se flight book karne ko kehti hai, toh airline ki API ko asal mein kaun bula raha hai? Asha nahi: woh so rahi hai. Koi bhi program nahi: use saabit karna hoga woh kya hai. Agents naye tarah ke user hain, non-human identity, aur insaanon ki taraf se kaam karte hain. Agent ko apna password, ya har permission wali hamesha chalne wali API key dena, wahi raasta hai jisse prompt injection (Ch 27) asli nuksaan banta hai. Yeh chapter woh pattern dikhaata hai jo ise rokta hai: har agent ki apni pehchaan, aur har action ke saath chhote samay ka token jo bataaye kaun, kiske liye, kya aur kab tak.

1

Four questions every tool call must answerChaar sawaal jinka jawab har tool call ko dena hai

Who is calling? A specific agent (travel-bot), not "the AI". On behalf of whom? Asha, who delegated the task. What may it do? Read her calendar and search flights; not book, not pay. Until when? Fifteen minutes. A token that carries these four answers, signed by an identity provider so it can't be edited, lets every tool server check the call by itself, with no trust in what the model claims.

Kaun bula raha hai? Ek khaas agent (travel-bot), "AI" nahi. Kiski taraf se? Asha, jisne kaam saunpa. Kya kar sakta hai? Uska calendar padhna aur flights search karna; book nahi, pay nahi. Kab tak? Pandrah minute. Jo token yeh chaaron jawab le kar chale, identity provider se signed taaki badla na ja sake, woh har tool server ko call khud check karne deta hai, model ke daave par bharosa kiye bina.

2

Least privilege, for minutes not monthsKam se kam adhikaar, mahino nahi minuton ke liye

Two habits do most of the work. Narrow scopes: give exactly the permissions this task needs. Short lifetimes: minutes, renewed as needed. If an agent is tricked by an injected instruction, the damage is limited to what its current token allows, for as long as it lasts. When a riskier action is needed (booking, paying), don't widen the existing token; ask the human, then issue a new token for that one action.

Do aadatein zyaadatar kaam karti hain. Patle scopes: theek wahi permissions do jo is kaam ko chahiye. Chhoti umar: minute, zaroorat par naye. Agar agent kisi injected instruction se bahak jaaye, nuksaan sirf utna jitna uska maujooda token allow kare, jab tak woh chale. Jab zyaada risky action chahiye (booking, payment), maujooda token chauda mat karo; insaan se poochho, phir sirf us ek action ke liye naya token do.

def issue(agent, on_behalf_of, scopes, ttl_s, now):
    claims = {"sub": agent, "act_for": on_behalf_of, "scope": scopes, "exp": now + ttl_s}
    body = b64(claims)
    return body + "." + hmac_sha256(SECRET, body)        # signed: any edit breaks it

def tool_server(token, action, now):
    claims = verify(token, now)                          # signature + expiry
    allowed = action in claims["scope"]                  # least privilege
    AUDIT.append((now, claims["sub"], claims["act_for"], action, allowed))

3

Delegation, OAuth and MCPDelegation, OAuth aur MCP

The industry standard for "let this app act for me, with these permissions" is OAuth 2.0: the familiar "Allow this app to read your calendar?" screen. The user approves scopes once; the app receives tokens, never the password. MCP (Ch 18) uses OAuth for remote servers: when an AI app connects to a company's MCP server, the user signs in and grants scopes, and the server checks those scopes on every tool call. For agent-to-agent calls, token exchange (OAuth's "on-behalf-of" flow) lets agent A get a narrower token to call agent B for the same user, so the chain of who-acted-for-whom stays visible.

"Is app ko in permissions ke saath meri taraf se kaam karne do" ka industry standard hai OAuth 2.0: jaani-pehchaani "Kya is app ko aapka calendar padhne dein?" screen. User ek baar scopes manzoor karta hai; app ko tokens milte hain, password kabhi nahi. MCP (Ch 18) remote servers ke liye OAuth use karta hai: jab AI app kisi company ke MCP server se judti hai, user sign in karke scopes deta hai, aur server har tool call par woh scopes check karta hai. Agent-se-agent calls ke liye token exchange (OAuth ka "on-behalf-of" flow) agent A ko usi user ke liye agent B ko bulaane ka patla token dilaata hai, taaki kisne-kiske-liye-kiya ki kadi dikhti rahe.

In the real world

The audit question every regulator asksHar regulator ka audit sawaal

"Who approved this payment?" must never be answered with "the AI did". With per-agent identities, delegation and an audit log, the answer is precise: travel-bot, acting for Asha, under a token issued at 10:42 after her approval, booked flight 6E-512. That record is what makes agents acceptable to banks, hospitals and governments (Book 2, Ch 12).

"Is payment ko kisne manzoor kiya?" ka jawab kabhi "AI ne" nahi hona chahiye. Har agent ki pehchaan, delegation aur audit log ke saath jawab sateek hai: travel-bot ne, Asha ki taraf se, uski manzoori ke baad 10:42 par jaari token ke tahat, flight 6E-512 book ki. Yahi record agents ko banks, hospitals aur sarkaaron ke liye sweekaarya banaata hai (Book 2, Ch 12).

What we learnedHumne kya seekha

  1. Every agent gets its own identity; never share a human's password or a forever key.
  2. Tokens say who, for whom, what and until when, and are signed so they can't be edited.
  3. Narrow scopes and short lifetimes limit the damage of a tricked agent.
  4. Risky actions get a new, single-purpose token after human approval.
  5. OAuth is the standard for delegation; MCP uses it; audit logs record every decision.
  1. Har agent ki apni pehchaan; insaan ka password ya hamesha wali key kabhi share nahi.
  2. Tokens batate hain kaun, kiske liye, kya aur kab tak, aur signed hote hain taaki badle na jaa sakein.
  3. Patle scopes aur chhoti umar bahke hue agent ka nuksaan seemit karte hain.
  4. Risky actions ko insaani manzoori ke baad naya, ek-kaam ka token.
  5. OAuth delegation ka standard hai; MCP use karta hai; audit logs har faisla likhte hain.
