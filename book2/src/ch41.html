Some agent tasks take seconds. Others take hours or days: onboarding a new employee across six systems, migrating a codebase, chasing a refund through a payment provider, waiting for a manager to approve something. Over that time, servers restart, APIs time out and people go home. A long-running agent must survive all of it without forgetting where it was and, above all, without doing a dangerous step twice. This chapter covers the four ideas that make that possible: state management, durable execution, a control plane, and harness-as-code.

Kuch agent kaam seconds lete hain. Kuch ghante ya din: naye employee ko chhe systems mein onboard karna, codebase migrate karna, payment provider ke zariye refund ka peechha karna, manager ki manzoori ka intezaar. Is dauraan servers restart hote hain, APIs time out hoti hain aur log ghar chale jaate hain. Lamba chalne wala agent yeh sab jhel ke bhi bhoolna nahi chahiye ki woh kahan tha, aur sabse zaroori, koi khatarnaak step do baar nahi karna chahiye. Yeh chapter woh chaar ideas samjhaata hai jo yeh mumkin banaate hain: state management, durable execution, control plane, aur harness-as-code.

1

State lives outside the modelState model ke bahar rehti hai

Haron forgets everything between calls. So the harness keeps the state: which steps are done, which are pending, the data each step produced (order details, IDs), money spent, files changed, and who approved what. Keep it somewhere that survives a crash: a database row, not a Python variable. The conversation transcript is not state; it's a log. If a step's result matters later, store it as data, with a name.

Haron do calls ke beech sab bhool jaata hai. Isliye harness state rakhta hai: kaunse steps ho gaye, kaunse baaki, har step ne kya data banaaya (order details, IDs), kitna paisa kharch hua, kaunsi files badli, aur kisne kya manzoor kiya. Ise aisi jagah rakho jo crash jhel le: database ki row, Python variable nahi. Baatcheet ka transcript state nahi hai; woh log hai. Agar kisi step ka nateeja baad mein kaam aaye, use naam ke saath data ki tarah store karo.

2

Durable execution: crash, resume, never repeatDurable execution: crash, resume, kabhi dohraana nahi

The rule is simple: write a checkpoint after every step. When the process restarts, it reads the checkpoint, skips everything already done, and continues. Two details make it safe. Write checkpoints atomically (write a temp file, then rename), so a crash never leaves half a record. And make risky steps idempotent: doing them twice has the same effect as once. Payment APIs support this with an idempotency key: send the same key again and the provider returns the first result instead of charging again. Engines such as Temporal, Restate, AWS Step Functions and LangGraph's checkpointers package this pattern so you don't build it by hand.

Niyam seedha hai: har step ke baad checkpoint likho. Process restart ho toh checkpoint padho, jo ho chuka woh chhodo, aage badho. Do details ise surakshit banaate hain. Checkpoints atomically likho (temp file likho, phir rename karo), taaki crash kabhi aadha record na chhode. Aur risky steps ko idempotent banao: do baar karne ka asar ek baar jaisa ho. Payment APIs isme idempotency key se madad karti hain: wahi key dobara bhejo toh provider dobara charge karne ki jagah pehla nateeja lautaata hai. Temporal, Restate, AWS Step Functions aur LangGraph ke checkpointers jaise engines is pattern ko tayyar dete hain, taaki haath se na banana pade.

3

The control plane decides; the agent doesControl plane tay karta hai; agent karta hai

Split your system in two. The data plane does the work: model calls, tool calls, file edits. The control plane decides whether each piece of work may happen: is this tool allowed for this agent? Is the amount under the limit? Has a human approved? Is the budget left? Because the control plane is plain code with plain rules, it can't be talked out of a decision by a clever prompt. That's the single most important safety property of an agent platform (Book 2, Ch 11 and 12 build this for a whole company).

Apne system ko do mein baanto. Data plane kaam karta hai: model calls, tool calls, file edits. Control plane tay karta hai ki har kaam ho sakta hai ya nahi: kya yeh tool is agent ke liye allowed hai? Kya rakam limit ke andar hai? Kya insaan ne manzoori di? Kya budget bacha hai? Kyunki control plane saada code aur saade niyam hai, koi chaalaak prompt use faisle se hata nahi sakta. Agent platform ki sabse zaroori suraksha yahi hai (Book 2, Ch 11 aur 12 ise poori company ke liye banaate hain).

4

Harness-as-codeHarness-as-code

Prompts, tool lists, limits, approval rules and model choices are behaviour. Treat them like code: keep them in a file in git, review changes in pull requests, run the eval suite (Ch 26) on every change, and roll back with one command. "Someone edited the system prompt in a web console last Tuesday" should never be the answer to "why did the agent start refunding everything?"

Prompts, tool lists, limits, approval rules aur model ke chunaav behaviour hain. Inhe code ki tarah maano: git mein file mein rakho, pull requests mein badlaav review karo, har badlaav par eval suite (Ch 26) chalao, aur ek command se wapas lo. "Kisi ne pichhle mangalvaar web console mein system prompt badal diya" kabhi bhi "agent sab kuch refund kyun karne laga?" ka jawab nahi hona chahiye.

HARNESS = {                                       # harness-as-code: reviewed, versioned data
    "steps": ["fetch_order", "check_policy", "issue_refund", "email_customer", "close_ticket"],
    "limits": {"max_refund_inr": 5000},
    "needs_approval": ["issue_refund"],          # human approval gate for money movement
}

for step in HARNESS["steps"]:
    if step in state["done"]:
        continue                                  # resume: skip finished steps
    decision = control_plane(step, state, approved)
    if decision != "allow":
        return                                    # wait for a human, or deny
    run(step, state)
    state["done"].append(step)
    save(state)                                   # atomic checkpoint after EVERY step

AI behaviour

Models are not deterministic; your workflow should beModels deterministic nahi; aapka workflow hona chahiye

Ask a model the same thing twice and you may get two different plans (even at temperature 0, as the Chapter 2 lab shows). So never let a resumed run re-ask the model what to do for a step that already happened: record the model's decision in the state the first time, and replay it. Do in plain code everything that doesn't need judgement (deterministic execution); use the model only where judgement is needed.

Model se ek hi baat do baar poochho toh do alag plans mil sakte hain (temperature 0 par bhi, jaisa Chapter 2 ka lab dikhaata hai). Isliye resume hue run ko kabhi us step ke liye model se dobara mat poochhne do jo ho chuka: pehli baar model ka faisla state mein likho, aur use dohraao. Jis kaam mein samajh ki zaroorat nahi, woh saade code mein karo (deterministic execution); model sirf wahan jahan samajh chahiye.

What we learnedHumne kya seekha

  1. Keep agent state in durable storage, as named data, not in the transcript.
  2. Checkpoint after every step, atomically; resume by skipping finished steps.
  3. Make risky steps idempotent so a retry can't pay or send twice.
  4. A control plane of plain rules approves, limits or blocks every action.
  5. Keep prompts, tools and policies in git as harness-as-code, and test every change.
  1. Agent ki state tikaau storage mein, naam wale data ki tarah rakho, transcript mein nahi.
  2. Har step ke baad atomically checkpoint; poore steps chhod kar resume.
  3. Risky steps idempotent banao taaki retry do baar pay ya send na kare.
  4. Saade niyamon ka control plane har action ko manzoor, seemit ya band karta hai.
  5. Prompts, tools aur policies git mein harness-as-code ki tarah rakho, aur har badlaav test karo.
