Where the seconds goSecond kahan jaate hain

One request has two phases. Reading your prompt (time to first token) grows with prompt length. Writing the answer takes time per output token, and that's usually the bigger part. So the two biggest speed levers are: send less, and ask for less.

Ek request ke do hisse hain. Prompt padhna (pehle token tak ka samay) prompt ki lambaai ke saath badhta hai. Jawab likhna har output token ka samay leta hai, aur aksar yahi bada hissa hai. Isliye speed ke do sabse bade levers: kam bhejo, aur kam maango.

AI behaviour

Cheaper settings can change behaviourSaste settings behaviour badal sakte hain

A smaller model, lower effort or a stricter output cap can quietly drop quality on hard cases: shorter reasoning, missed edge cases, truncated JSON. That's why every cost change goes through the same eval gate as a prompt change. Judge cost per successful task, not cost per call: a cheap call that needs three retries isn't cheap.

Chhota model, kam effort ya sakht output limit mushkil cases par chupchaap quality gira sakte hain: chhoti reasoning, chhoote edge cases, kata JSON. Isliye har kharch badlaav usi eval gate se jaata hai jisse prompt badlaav. Har safal kaam ka kharch dekho, har call ka nahi: teen retries wali sasti call sasti nahi.

Engineer's note

Don't break your own cacheApni cache khud mat todo

Caching only works on an exact prefix. A timestamp, a user name or a randomly ordered tool list at the top of the prompt makes every request a cache miss. Keep the stable parts first and identical (sorted JSON, fixed tool order), put volatile values at the end, and check the provider's usage fields for cache-read tokens to confirm it's working.

Caching sirf sateek prefix par chalti hai. Prompt ke upar timestamp, user ka naam ya random order wali tool list har request ko cache miss bana deti hai. Sthir hisse pehle aur bilkul same rakho (sorted JSON, fixed tool order), badalti values aakhir mein, aur kaam kar raha hai yeh confirm karne ke liye provider ke usage fields mein cache-read tokens check karo.

In the real world

Perceived speed matters as much as real speedMehsoos hone wali speed asli speed jitni zaroori

Streaming the first words in under a second makes a 10-second answer feel fast. Showing progress ("Checking your order…") during tool calls keeps users patient. For work nobody waits for (nightly reports, bulk tagging), use the batch API at about half price and let it take hours.

Second se kam mein pehle words stream karna 10 second ke jawab ko tez mehsoos karaata hai. Tool calls ke dauraan progress dikhaana ("Aapka order check kar raha hoon…") users ko dhairya deta hai. Jis kaam ka koi intezaar nahi karta (raat ki reports, bulk tagging), uske liye lagbhag aadhe daam par batch API use karo aur ghanton lene do.

What we learnedHumne kya seekha

  1. Writing is the slow, pricey part: ask for shorter output.
  2. Free wins first: caching, trimming context, capping output, streaming.
  3. Then trade-offs: batch, lower effort, smaller models and routing, each checked by evals.
  4. Measure cost per successful task.
  1. Likhna dheema, mehenga hissa hai: chhota output maango.
  2. Pehle muft jeet: caching, context chhota, output limit, streaming.
  3. Phir sauda: batch, kam effort, chhote models aur routing, har ek evals se check.
  4. Har safal kaam ka kharch naapo.
