Every company has a database full of answers that managers can't reach without asking an analyst: "What was delivered revenue in Pune last month?", "Which customers ordered twice?". Text-to-SQL lets them ask in plain words: the model writes the SQL query, the database runs it, and the numbers come back. It's one of the most-requested AI features in companies, and one of the easiest to get dangerously wrong. This chapter builds it safely.

Har company ke paas jawabon se bhara database hai jahan managers analyst se poochhe bina nahi pahunch sakte: "Pichhle mahine Pune mein delivered revenue kitna tha?", "Kin customers ne do baar order kiya?". Text-to-SQL unhe saade shabdon mein poochhne deta hai: model SQL query likhta hai, database chalaata hai, aur numbers wapas aate hain. Companies mein yeh sabse zyaada maange jaane wale AI features mein se hai, aur khatarnaak tareeke se galat karne mein sabse aasaan bhi. Yeh chapter ise surakshit banaata hai.

The pipelinePipeline

The model has never seen your database. So the context carries the schema (tables, columns, how they join) plus notes a new analyst would need: which values a status column can take, how dates are stored, what "revenue" means here (delivered orders only? before or after tax?). Business definitions matter more than SQL skill: most wrong answers in production are correct SQL for the wrong definition.

Model ne aapka database kabhi nahi dekha. Isliye context mein schema jaata hai (tables, columns, kaise judte hain) plus woh notes jo naye analyst ko chahiye: status column mein kaunsi values ho sakti hain, dates kaise store hain, yahan "revenue" ka matlab kya hai (sirf delivered orders? tax se pehle ya baad?). Business ki paribhaasha SQL ke hunar se zyaada zaroori hai: production mein zyaadatar galat jawab galat paribhaasha ke liye sahi SQL hote hain.

Safety first: the model never gets write accessPehle suraksha: model ko kabhi likhne ka adhikaar nahi

A user, or an injected instruction in some text, can ask for "delete all cancelled orders". Defend in layers. Run queries on a read-only database user or replica. Before running, a guard in plain code accepts only a single SELECT and rejects write or admin keywords. Add a row limit and a timeout so one heavy query can't freeze the database. And filter by permissions: a sales intern shouldn't be able to query the salaries table just because the model can write the JOIN.

User, ya kisi text mein injected instruction, "saare cancelled orders delete karo" maang sakta hai. Parton mein bachaav karo. Queries read-only database user ya replica par chalao. Chalaane se pehle saade code ka guard sirf ek SELECT maane aur write ya admin keywords thukraaye. Row limit aur timeout jodo taaki ek bhaari query database na jama de. Aur permissions se filter karo: sales intern sirf isliye salaries table query na kar sake ki model JOIN likh sakta hai.

prompt = f"SQLite schema:\n{SCHEMA}\nNotes: {NOTES}\n\nWrite ONE SQLite SELECT query that answers: {question}"
sql = extract_sql(chat(prompt))
for attempt in (1, 2):
    if problem := guard(sql):                       # only one read-only SELECT passes
        return f"BLOCKED: {problem}"
    try:
        return DB.execute(sql).fetchall()           # connection is also read-only
    except sqlite3.Error as e:
        sql = extract_sql(chat(prompt + f"\nYour query:\n{sql}\nfailed with: {e}\nFix it."))
3

Is the answer right?Kya jawab sahi hai?

A query that runs isn't a query that's right. Evaluate text-to-SQL by executing both the model's query and a trusted reference query on the same data and comparing the results, not by comparing SQL text (there are many correct ways to write a query). Build a test set of 50 real questions from your users with analyst-written SQL; run it on every prompt or model change (Ch 26). In the product, show the SQL and the row count next to the answer, so a curious user can check, and say "I'm not sure" when a question doesn't map to the schema.

Jo query chal jaaye woh sahi ho, zaroori nahi. Text-to-SQL ka evaluation model ki query aur ek bharosemand reference query dono ko ek hi data par chala kar nateeje milaakar karo, SQL text milaakar nahi (query likhne ke kai sahi tareeke hain). Apne users ke 50 asli sawaalon ka test set analyst ki likhi SQL ke saath banao; har prompt ya model badlaav par chalao (Ch 26). Product mein jawab ke saath SQL aur row count dikhao, taaki jigyaasu user jaanch sake, aur jab sawaal schema se na jude toh "pakka nahi pata" kaho.

In the real world

A semantic layer beats a bigger modelSemantic layer bade model se behtar

Large companies have hundreds of tables with names like t_ord_hdr_v2. Instead of dumping all of that into the context, they give the model a curated semantic layer: a short list of business metrics ("delivered revenue", "active customer") with their exact definitions and the approved SQL behind them. The model picks metrics and filters; the layer writes the SQL. Accuracy goes up, and finance and sales finally get the same number.

Badi companies mein t_ord_hdr_v2 jaise naamon wali saikdon tables hoti hain. Yeh sab context mein daalne ki jagah woh model ko chuni hui semantic layer dete hain: business metrics ki chhoti list ("delivered revenue", "active customer") unki sateek paribhaasha aur manzoor SQL ke saath. Model metrics aur filters chunta hai; layer SQL likhti hai. Sateekta badhti hai, aur finance aur sales ko aakhir ek hi number milta hai.

What we learnedHumne kya seekha

  1. Put the schema and business definitions in the context; definitions matter more than SQL skill.
  2. Read-only access, a code guard that allows one SELECT, row limits, timeouts and permission filters.
  3. Feed database errors back once for repair.
  4. Evaluate by executing and comparing results; show the SQL to users.
  5. At company scale, a semantic layer beats raw tables.
  1. Context mein schema aur business paribhaashayein do; paribhaasha SQL ke hunar se zyaada zaroori.
  2. Read-only access, ek SELECT allow karne wala code guard, row limits, timeouts aur permission filters.
  3. Database errors ek baar repair ke liye wapas do.
  4. Chala kar nateeje milaakar evaluate karo; users ko SQL dikhao.
  5. Company scale par semantic layer kachchi tables se behtar.
