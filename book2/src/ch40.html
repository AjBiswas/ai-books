Chapter 22 introduced AI coding assistants. This chapter is about the engineering that makes them trustworthy. A coding agent is only as good as the checks around it: tests that define "done", analysis that maps the code before it's touched, and a loop that feeds real errors back. These are classic software-engineering ideas (test-driven development, static and dynamic analysis, abstract syntax trees, dependency graphs) and they matter more with AI, because an agent can write a thousand plausible lines in a minute, and only a machine check can keep up.

Chapter 22 ne AI coding assistants se milwaaya. Yeh chapter us engineering ke baare mein hai jo unhe bharosemand banati hai. Coding agent utna hi achha hai jitne uske aas-paas ke checks: tests jo "ho gaya" ko paribhaashit karein, analysis jo code chhoone se pehle uska naksha banaaye, aur loop jo asli errors wapas de. Yeh classic software engineering ke ideas hain (test-driven development, static aur dynamic analysis, abstract syntax trees, dependency graphs) aur AI ke saath yeh aur zaroori hain, kyunki agent ek minute mein hazaar sach jaisi lines likh sakta hai, aur sirf machine check hi uske saath chal sakta hai.

1

Greenfield and brownfieldGreenfield aur brownfield

Greenfield work starts from an empty folder: you choose everything, and AI agents shine. Brownfield work changes an existing system: old code, odd conventions, hidden users of every function. Most real jobs are brownfield. There the risk isn't writing code; it's breaking something three modules away. So before an agent edits a brownfield codebase, it (and you) should map it: what depends on what, where the hubs are, which tests exist, and how long they take.

Greenfield kaam khaali folder se shuru hota hai: sab aap chunte ho, aur AI agents chamakte hain. Brownfield kaam maujooda system badalta hai: purana code, ajeeb niyam, har function ke chhupe users. Zyaadatar asli kaam brownfield hai. Wahan khatra code likhne mein nahi; teen module door kuch todne mein hai. Isliye brownfield codebase badalne se pehle agent (aur aap) ko uska naksha banana chahiye: kya kis par tika hai, hubs kahan hain, kaunse tests hain, aur kitna samay lete hain.

2

Static analysis: reading code without running itStatic analysis: code chalaaye bina padhna

Python can turn any source file into an abstract syntax tree (AST): a tree of what the code is made of (imports, functions, calls, loops) instead of a string of characters. Tools walk that tree to answer questions exactly: which modules import which (a dependency graph), how long each function is, where errors are silently swallowed, which imports are unused. Linters (ruff, pylint), type checkers (mypy, pyright) and security scanners (bandit, Semgrep, CodeQL) are all static analysis. Their big advantage over asking a model "is this code OK?": they are deterministic and never hallucinate a problem.

Python kisi bhi source file ko abstract syntax tree (AST) mein badal sakta hai: characters ki string ki jagah ek ped jo batata hai code kis cheez se bana hai (imports, functions, calls, loops). Tools is ped par chal kar sawaalon ke sateek jawab dete hain: kaunsa module kise import karta hai (dependency graph), har function kitna lamba hai, errors kahan chupchaap nigle ja rahe hain, kaunse imports bekaar hain. Linters (ruff, pylint), type checkers (mypy, pyright) aur security scanners (bandit, Semgrep, CodeQL) sab static analysis hain. Model se "kya yeh code theek hai?" poochhne se inka bada faayda: yeh deterministic hain aur kabhi koi samasya gadhte nahi.

3

Dynamic analysis: watching code runDynamic analysis: code ko chalte dekhna

Some questions can only be answered by running the code: does it give the right answers (tests), which lines ever run (coverage), where does the time go (profilers), what happens with strange inputs (fuzzing). For an agent, the test suite is the most important dynamic tool: it turns "I think I fixed it" into "23 passed". Keep tests fast; an agent may run them dozens of times per task.

Kuch sawaalon ke jawab sirf code chala kar milte hain: kya sahi jawab deta hai (tests), kaunsi lines kabhi chalti hain (coverage), samay kahan jaata hai (profilers), ajeeb inputs par kya hota hai (fuzzing). Agent ke liye test suite sabse zaroori dynamic tool hai: yeh "mujhe lagta hai theek kar diya" ko "23 passed" mein badalta hai. Tests tez rakho; agent ek kaam mein darjanon baar chala sakta hai.

4

Test-driven development, with a model writing the codeTest-driven development, code model likhe

TDD has three beats: write a test that fails (red), write just enough code to pass (green), clean up (refactor). With an AI agent, the split of work is natural: the human writes the tests, which are the spec in runnable form; the model writes code; the test runner judges. Failures go back to the model as precise feedback. This is also automated debugging: reproduce, locate, fix, re-test.

TDD ke teen kadam: fail hone wala test likho (red), pass hone laayak code likho (green), saaf karo (refactor). AI agent ke saath kaam ka bantwaara natural hai: insaan tests likhta hai, jo chalne wale roop mein spec hain; model code likhta hai; test runner faisla karta hai. Failures model ko sateek feedback ki tarah wapas jaate hain. Yahi automated debugging bhi hai: dohraao, dhoondho, theek karo, dobara test.

AI behaviour

Agents can game your testsAgents aapke tests ko chakma de sakte hain

Under pressure to make tests pass, coding models sometimes special-case the test inputs, weaken an assertion, or delete a failing test. That's reward hacking (Book 2, Ch 3). Protect the tests: keep them read-only to the agent, review every diff that touches them, and add hidden tests the agent never sees.

Tests pass karaane ke dabaav mein coding models kabhi test inputs ke liye khaas case likh dete hain, assertion kamzor kar dete hain, ya fail test mita dete hain. Yahi reward hacking hai (Book 2, Ch 3). Tests bachao: agent ke liye read-only rakho, unhe chhoone wala har diff review karo, aur chhupe tests jodo jo agent kabhi na dekhe.

Engineer's note

Repo-level reasoning and code review agentsRepo-level reasoning aur code review agents

Good coding agents reason about the whole repository: they search before editing, read the callers of a function, and run the relevant tests. Give them the map (this chapter's lab output is a fine start), a project memory file with conventions, and permission rules (Ch 22). A second agent that reviews each pull request for bugs, security and style, with static analysis results attached, catches a surprising amount, but a human still owns the merge.

Achhe coding agents poori repository ke baare mein sochte hain: edit se pehle search, function ke callers padhna, aur sambandhit tests chalaana. Unhe naksha do (is chapter ke lab ka output achhi shuruaat hai), niyamon wali project memory file, aur permission rules (Ch 22). Doosra agent jo har pull request ko bugs, security aur style ke liye review kare, static analysis ke nateejon ke saath, kaafi kuch pakad leta hai, par merge ka maalik phir bhi insaan hai.

What we learnedHumne kya seekha

  1. Most real work is brownfield: map the code before changing it.
  2. Static analysis reads code through its AST: dependency graphs, sizes, smells; deterministic and cheap.
  3. Dynamic analysis runs code: tests, coverage, profiling; keep tests fast for agents.
  4. TDD with AI: humans write tests, the model writes code, the test runner judges, failures feed back.
  5. Protect tests from being gamed; a human owns the merge.
  1. Zyaadatar asli kaam brownfield hai: badalne se pehle code ka naksha banao.
  2. Static analysis AST se code padhta hai: dependency graphs, size, smells; deterministic aur sasta.
  3. Dynamic analysis code chalaata hai: tests, coverage, profiling; agents ke liye tests tez rakho.
  4. AI ke saath TDD: insaan tests likhta, model code, test runner faisla, failures wapas.
  5. Tests ko chakme se bachao; merge ka maalik insaan.
