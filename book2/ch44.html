Deploying Models: Docker, Kubernetes, GPUsModels Deploy Karna: Docker, Kubernetes, GPUs

Calling a provider's API (Ch 5) is the easy way to use a model. Sometimes you must run it yourself: the data can't leave your network, the volume makes per-token prices too high, or you need an open model you've fine-tuned. Then you become the provider. This chapter covers what that means in practice: will the model fit on the GPU, which serving engine to use, how to package your service in a container, and how Kubernetes keeps it running and scales it.

Provider ki API bulaana (Ch 5) model use karne ka aasaan tareeka hai. Kabhi-kabhi khud chalaana padta hai: data aapke network se bahar nahi ja sakta, volume itna hai ki per-token daam bahut zyaada, ya aapko apna fine-tune kiya open model chahiye. Tab aap khud provider ban jaate ho. Yeh chapter iska asli matlab samjhaata hai: kya model GPU mein fit hoga, kaunsa serving engine, service ko container mein kaise pack karein, aur Kubernetes use kaise chalaata aur scale karta hai.

Will it fit? GPU memory mathsKya fit hoga? GPU memory ka hisaab

GPU memory holds two big things. The weights: parameters × bytes per parameter (16-bit = 2 bytes, 8-bit = 1, 4-bit = 0.5). And the KV cache (Ch 38): for every token of every conversation in flight, each layer stores a key and a value. Weights are fixed; the KV cache grows with users × context length. That's why a model that "fits" for one user can run out of memory at lunchtime.

GPU memory do badi cheezein rakhti hai. Weights: parameters × har parameter ke bytes (16-bit = 2 bytes, 8-bit = 1, 4-bit = 0.5). Aur KV cache (Ch 38): chal rahi har baatcheet ke har token ke liye, har layer ek key aur ek value rakhti hai. Weights tay hain; KV cache users × context length ke saath badhta hai. Isiliye jo model ek user ke liye "fit" hota hai, woh lunch ke samay memory se bahar ho sakta hai.

Serving enginesServing engines

Don't serve a model with a for-loop. Serving engines squeeze far more out of a GPU with continuous batching (new requests join a running batch every step), paged KV cache (memory handed out in small pages, so nothing is wasted), prefix caching and speculative decoding (Ch 24, 29). Pick by situation:

Model ko for-loop se serve mat karo. Serving engines GPU se kahin zyaada nikaalte hain continuous batching (nayi requests har step chalte batch mein judti hain), paged KV cache (memory chhote pages mein di jaati hai, kuch barbaad nahi), prefix caching aur speculative decoding (Ch 24, 29) se. Your API service in front of the engineEngine ke aage aapki API service

Never expose the engine directly. Put a thin service in front that checks API keys, records which team used how many tokens, applies rate limits, exposes a /healthz endpoint for probes, and speaks the OpenAI-compatible format so every client library works unchanged. In a company this grows into the gateway of Book 2, Chapter 11.

Engine ko kabhi seedha bahar mat kholo. Aage ek patli service rakho jo API keys check kare, kis team ne kitne tokens use kiye likhe, rate limits lagaaye, probes ke liye /healthz endpoint de, aur OpenAI-compatible format bole taaki har client library bina badlaav chale. Company mein yahi Book 2, Chapter 11 ka gateway ban jaata hai.

Containers and KubernetesContainers aur Kubernetes

A container (Docker) packs your service with exactly the Python version and libraries it needs, so it runs the same on your laptop and in production. Kubernetes runs many containers across many machines: it restarts crashed ones, sends traffic only to pods whose readiness probe passes (a model can take minutes to load), gives each pod a GPU, and adds pods when load rises (autoscaling). GPUs are expensive, so autoscale on what really measures load for LLMs, such as the number of waiting requests, and set a maximum so a traffic spike can't empty your budget.

Container (Docker) aapki service ko theek wahi Python version aur libraries ke saath pack karta hai jo chahiye, taaki laptop aur production mein ek jaisi chale. Kubernetes kai machines par kai containers chalaata hai: crash hue ko restart karta hai, traffic sirf un pods ko bhejta hai jinka readiness probe pass ho (model load hone mein minutes lag sakte hain), har pod ko GPU deta hai, aur load badhne par pods jodta hai (autoscaling). GPUs mehenge hain, isliye us cheez par autoscale karo jo LLMs ka load sach mein naapti hai, jaise intezaar karti requests, aur maximum tay karo taaki traffic ka uchhaal budget khaali na kar de.

In the real world

Self-host or call an API?Khud host karein ya API bulaayein?

A single always-on cloud GPU costs roughly as much per month as millions of API calls to a small model. Self-hosting pays off when volume is high and steady, when data must stay in your network (some banks and hospitals in India), or when you serve your own fine-tuned model. Otherwise, start with an API and revisit when the bill or the rules force it.

Ek hamesha chalta cloud GPU mahine mein lagbhag utna kharch karta hai jitna chhote model ki laakhon API calls. Khud host karna tab faayde ka hai jab volume zyaada aur sthir ho, jab data aapke network mein rehna zaroori ho (India mein kuch banks aur hospitals), ya jab aap apna fine-tune kiya model serve karo. Warna API se shuru karo aur jab bill ya niyam majboor karein tab dobara socho.

What we learnedHumne kya seekha

  1. GPU memory = weights + KV cache; the KV cache grows with users × context.
  2. Use a serving engine (vLLM and friends) for batching and paged KV cache.
  3. Put a thin API service in front: keys, usage, rate limits, health checks.
  4. Containers make it portable; Kubernetes restarts, probes and scales it, with a cap on GPUs.
  1. GPU memory = weights + KV cache; KV cache users × context ke saath badhta hai.
  2. Batching aur paged KV cache ke liye serving engine (vLLM jaise) use karo.
  3. Aage patli API service rakho: keys, usage, rate limits, health checks.
