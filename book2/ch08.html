Structured OutputsStructured Outputs

People read paragraphs. Programs don't. When your code needs Haron's answer as data (a ticket category, an invoice total, a list of names), "please reply in JSON" works most of the time. Most of the time is not good enough for software that runs a million times. This chapter turns "most of the time" into "every time".

Log paragraphs padhte hain. Programs nahi. Jab aapke code ko Haron ka jawab data ki tarah chahiye (ticket category, invoice total, naamon ki list), "please JSON mein jawab do" zyaadatar kaam karta hai. Zyaadatar, das laakh baar chalne wale software ke liye kaafi nahi. Yeh chapter "zyaadatar" ko "har baar" banata hai.

2

The guard at every tokenHar token par guard

Remember the lucky wheel from Chapter 2: at every step, every token has a chance. Constrained decoding puts a guard on the wheel. Before each spin, it covers every slice that would break your schema. If the schema says issue must be one of four words, only those four can come out. The output is valid by construction.

Chapter 2 ka lucky wheel yaad karo: har step par har token ka chance hai. Constrained decoding wheel par guard lagaata hai. Har spin se pehle woh har us hisse ko dhak deta hai jo aapka schema todega. Agar schema kehta hai issue chaar shabdon mein se ek ho, toh sirf wahi chaar nikal sakte hain. Output bante waqt hi valid hota hai.

3

Tested on a laptopLaptop par test kiya

Five real-looking tickets in English, Hinglish and Hindi-flavoured English, extracted by qwen3:4b, with and without a schema. The honest result: on these easy cases, both were 5/5 valid. The schema's value is the guarantee on the millionth messy ticket. But look closely at the urgency scores.

English, Hinglish aur Hindi-wali English mein paanch asli jaise tickets, qwen3:4b ne nikaale, schema ke saath aur bina. Imaandaar nateeja: in aasaan cases par dono 5/5 valid the. Schema ki keemat das-laakhve ulajhe ticket par guarantee hai. Par urgency scores dhyaan se dekho.

AI behaviour

Valid is not the same as correctValid hona sahi hona nahi hai

A schema guarantees the shape, not the truth. The model can still put the wrong city in a perfectly valid city field, or invent a value when the text doesn't contain one. Allow "unknown" (or null) for fields that may be missing, otherwise you force the model to make something up. And keep checking values with evals.

Schema shape ki guarantee deta hai, sach ki nahi. Model ab bhi bilkul valid city field mein galat shehar daal sakta hai, ya text mein value na ho toh bana sakta hai. Jo fields gaayab ho sakti hain unke liye "unknown" (ya null) allow karo, warna aap model ko kuch banaane par majboor karte ho. Aur evals se values check karte raho.

Engineer's note

Subjective fields need a rubricSubjective fields ko rubric chahiye

In the lab, "urgency" changed between runs (Suresh 3 → 5, Kavya 1 → 2) because "how urgent is this, 1–5?" is a judgement. Define the scale in the prompt: "5 = money lost or service down; 4 = deadline within 48 h; 3 = broken product; 2 = question with a mild complaint; 1 = general question". Now two runs, and two models, agree far more often.

Lab mein "urgency" runs ke beech badli (Suresh 3 → 5, Kavya 1 → 2) kyunki "yeh kitna urgent hai, 1–5?" ek faisla hai. Prompt mein scale define karo: "5 = paisa gaya ya service band; 4 = 48 ghante mein deadline; 3 = toota product; 2 = halki shikaayat ke saath sawaal; 1 = aam sawaal". Ab do runs, aur do models, kahin zyaada baar sahmat hote hain.

from pydantic import BaseModel
from typing import Literal

class Ticket(BaseModel):
    name: str
    city: str
    issue: Literal["refund", "delivery", "login", "other"]
    urgency: int

resp = client.messages.parse(model="claude-opus-5-5", max_tokens=1024,
                             messages=[{"role": "user", "content": ticket_text}],
                             output_format=Ticket)
ticket = resp.parsed_output          # a validated Ticket object

Check the SDK version you install for the exact parse helper names; the shape above follows Anthropic's Python SDK documentation.

✓

What we learnedHumne kya seekha

  1. "Reply in JSON" works often; a schema with constrained decoding works always.
  2. The schema guarantees shape, not truth; allow "unknown".
  3. Give subjective fields a written scale.
  4. Use enums, required fields and no extra properties.
  1. "JSON mein jawab do" aksar chalta hai; constrained decoding wala schema hamesha.
  2. Schema shape ki guarantee hai, sach ki nahi; "unknown" allow karo.
  3. Subjective fields ko likha hua scale do.
  4. Enums, required fields aur koi extra property nahi.
