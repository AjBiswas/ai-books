Haron's ExamsHaron ke Exams

A developer changes one sentence in Haron's system prompt and says: "I tried five questions, it's better now." Five questions prove nothing. Haron's answers vary, customers ask in many ways and many languages, and a change that helps one group can quietly break another. The team needs proper exams, called evals, that run on every change, give numbers with error bars, and block a release that makes things worse.

Ek developer Haron ke system prompt mein ek sentence badalta hai aur kehta hai: "Maine paanch sawaal try kiye, ab behtar hai." Paanch sawaal kuch saabit nahi karte. Haron ke jawab badalte rehte hain, customers kai tarah aur kai bhashaon mein poochte hain, aur jo badlaav ek group ki madad kare woh chupchaap doosre ko tod sakta hai. Team ko asli exams chahiye, jinhe evals kehte hain, jo har badlaav par chalein, error bars ke saath numbers dein, aur cheezein bigaadne wali release ko rok dein.

RememberYaad rakho

Always report a score with its confidence interval, compare versions case by case (paired), and look at slices: language, customer segment, task type. An average can go up while the customers who matter most get worse.

Score hamesha confidence interval ke saath batao, versions ko case-by-case (paired) compare karo, aur slices dekho: bhasha, customer segment, kaam ka type. Average badh sakta hai jabki sabse zaroori customers ke liye cheezein bigad jaayein.

When the examiner is also an AIJab examiner bhi AI ho

Some answers can be checked by code (is it valid JSON? does it contain "7 days"?). Many can't: is this reply polite, complete, correct for the policy? For those, a second model can grade against a rubric. It's fast and cheap, but it has its own biases, so first you check the judge against humans.

Kuch jawab code se check ho sakte hain (kya yeh valid JSON hai? kya isme "7 days" hai?). Kai nahi: kya yeh jawab vinamra, poora, policy ke hisaab se sahi hai? Unke liye doosra model rubric ke against grade kar sakta hai. Tez aur sasta hai, par uske apne biases hain, isliye pehle judge ko insaanon ke saath check karo.

AI behaviour

Judges have favouritesJudges ke bhi pasandeeda hote hain

LLM judges tend to prefer the first answer shown (position bias), longer answers (verbosity bias) and answers written by their own model family (self-preference). Countermeasures: swap the order and average, judge one answer at a time against a rubric with a reference answer, use a different model family as the judge, and measure agreement with human labels before trusting it.

LLM judges aksar pehle dikhaaye gaye jawab ko pasand karte hain (position bias), lambe jawab (verbosity bias) aur apne hi model family ke likhe jawab (self-preference). Upaay: order badalkar average lo, ek baar mein ek jawab rubric aur reference answer ke saath judge karo, judge ke liye alag model family lo, aur bharosa karne se pehle insaani labels ke saath sahmati naapo.

Enterprise

Evals are the contract between teamsEvals teams ke beech ka contract hain

Make every agent own a versioned eval suite, run it in CI on every prompt, tool or model change, and on a schedule against production models (providers update them). Gate releases on it. When a client asks "how do you know it works?", the eval report is your answer, and a growing set of real failure cases from production (with PII removed) is the most valuable dataset the company owns.

Har agent ka apna versioned eval suite ho, har prompt, tool ya model badlaav par CI mein chale, aur schedule par production models ke against bhi (providers unhe update karte hain). Release usi par gate karo. Jab client pooche "aapko kaise pata yeh chalta hai?", toh eval report jawab hai, aur production ke asli fail cases (PII hata kar) ka badhta set company ka sabse keemti dataset hai.

Deep dive: bootstrap, paired tests and pass@kGehraai mein: bootstrap, paired tests aur pass@kadvanced
pass@k = 1 − C(n−c, k) / C(n, k) (16.1)

Bootstrap CI: resample the per-case scores with replacement 2,000 times, compute the mean each time, and take the 2.5th and 97.5th percentiles. Paired comparison: compute the per-case difference (v2 − v1) and bootstrap that; this removes the noise of "some cases are just hard" and is far more sensitive than comparing two separate intervals. Gate: fail if the lower bound of the difference is below −tolerance. pass@k (Chen et al., 2021): with n samples per task of which c succeed, the chance that at least one of k tries succeeds; use it when an agent may retry, and pass^k (all k succeed) when it must be reliable every time.

Bootstrap CI: har case ke scores ko 2,000 baar replacement ke saath dobara chuno, har baar mean nikaalo, aur 2.5th aur 97.5th percentile lo. Paired comparison: har case ka farak (v2 − v1) nikaal kar uska bootstrap karo; isse "kuch cases bas mushkil hain" wala noise hat-ta hai aur do alag intervals compare karne se kahin zyaada sensitive hai. Gate: farak ki lower bound −tolerance se neeche ho toh fail. pass@k (Chen et al., 2021): har kaam ke n samples mein c safal hon, toh k koshishon mein kam se kam ek safal hone ka chance; jab agent retry kar sake tab use karo, aur pass^k (saare k safal) jab har baar bharosemand hona zaroori ho.

What we learnedHumne kya seekha

  1. Test me on many real cases, not five favourites.
  2. Report scores with error bars, compare case by case, and check every slice.
  3. An AI judge helps, once you've checked it against humans.
  4. For agents, check the actions and the end state, not just the words.
  5. No change ships unless the gate passes.
  1. Mujhe paanch pasandeeda nahi, kai asli cases par test karo.
  2. Scores error bars ke saath batao, case-by-case compare karo, aur har slice check karo.
  3. AI judge madad karta hai, jab tum use insaanon ke saath check kar lo.
  4. Agents ke liye shabd nahi, kaam aur aakhri sthiti check karo.
  5. Gate pass kiye bina koi badlaav ship nahi hota.
