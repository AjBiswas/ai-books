Watching Haron WorkHaron par Nazar

Evals check Haron before release. But after release, real customers ask things nobody tested, providers quietly update models, and a bug in one tool makes every run take three extra laps. You find out only if you are watching. Observability means that for any run you can answer: what happened, in what order, how long it took, what it cost, and whether it is getting worse.

Evals release se pehle Haron ko check karte hain. Par release ke baad asli customers aisi cheezein poochte hain jo kisi ne test nahi ki, providers chupchaap models update karte hain, aur ek tool ka bug har run mein teen extra chakkar lagwa deta hai. Pata tabhi chalta hai jab aap nazar rakh rahe ho. Observability ka matlab hai ki kisi bhi run ke liye aap bata sako: kya hua, kis order mein, kitna samay laga, kitna kharch hua, aur kya cheezein bigad rahi hain.

1

The trace: a run's X-rayTrace: run ka X-ray

A trace is one run drawn as a timeline. Each step is a span with a start, an end and labels (model, tokens, cost, tool name, error). Spans nest: the agent run contains model calls and tool calls. The OpenTelemetry project has standard names for AI spans (gen_ai.*), so any tracing tool can read them.

Trace ek run ko timeline ki tarah dikhata hai. Har step ek span hai jiska start, end aur labels hote hain (model, tokens, kharch, tool naam, error). Spans ek-doosre ke andar hote hain: agent run ke andar model calls aur tool calls. OpenTelemetry project ne AI spans ke standard naam rakhe hain (gen_ai.*), taaki koi bhi tracing tool unhe padh sake.

3

Spotting driftDrift pakadna

A provider updates its model behind the same name, and Haron's answers get 45% longer. No error is thrown; the bill just grows and customers scroll more. Compare this week's distribution of a signal (answer length, tool calls per run, refusal rate, judge score) with a baseline. The Population Stability Index (PSI) turns that into one number.

Provider usi naam ke peeche model update kar deta hai, aur Haron ke jawab 45% lambe ho jaate hain. Koi error nahi aata; bas bill badhta hai aur customers zyaada scroll karte hain. Is hafte ke kisi signal (jawab ki lambaai, har run ke tool calls, refusal rate, judge score) ke distribution ko baseline se compare karo. Population Stability Index (PSI) ise ek number mein badal deta hai.

AI behaviour

Failures are quietFailures chupchaap hote hain

Normal software crashes loudly. An AI system usually fails politely: a fluent wrong answer, an extra loop, a refusal that sounds reasonable. That's why you watch behaviour signals (refusal rate, steps per run, tool error rate, user thumbs-down, judge scores on a sample of live traffic), not just errors and latency.

Aam software zor se crash hota hai. AI system aksar vinamrata se fail hota hai: saaf galat jawab, ek extra chakkar, samajhdaar lagne wala inkaar. Isliye sirf errors aur latency nahi, behaviour signals dekho (refusal rate, har run ke steps, tool error rate, user ka thumbs-down, live traffic ke sample par judge scores).

The AI incident runbookAI incident runbook

  1. Detect: alerts on cost spikes, error rates, drift, injection hits, complaint keywords.
  2. Contain: a per-agent kill switch in the gateway; switch the route to a safe model or a human queue.
  3. Roll back: prompts, tools and model pins are versioned, so go back one version.
  4. Investigate: pull the traces and audit records for affected runs.
  5. Learn: add the failing cases to the eval suite so it can't happen silently again.
  1. Pakdo: kharch ke uchhaal, error rates, drift, injection hits, shikaayat ke keywords par alerts.
  2. Roko: gateway mein har agent ka kill switch; route ko surakshit model ya insaani queue par daalo.
  3. Wapas jao: prompts, tools aur model pins versioned hain, toh ek version peeche jao.
  4. Jaanch: prabhavit runs ke traces aur audit records nikaalo.
  5. Seekho: fail cases eval suite mein jodo taaki yeh dobara chupchaap na ho.
Deep dive: span attributes and PSIGehraai mein: span attributes aur PSIadvanced
PSI = Σbins (ai − ei) · ln(ai / ei) (17.1)

ei and ai are the fractions of the baseline and current samples in bin i. Rules of thumb: below 0.1 stable, 0.1–0.25 watch, above 0.25 investigate. Useful span attributes: gen_ai.system, gen_ai.request.model, gen_ai.response.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, plus your own (harness.tenant, harness.cost_usd, harness.policy_version, harness.stop_reason). Don't put raw prompts in spans by default; they are telemetry, often with wider access than the audit store.

ei aur ai bin i mein baseline aur current samples ke hisse hain. Mota hisaab: 0.1 se kam sthir, 0.1–0.25 nazar rakho, 0.25 se upar jaanch karo. Kaam ke span attributes: gen_ai.system, gen_ai.request.model, gen_ai.response.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, aur apne (harness.tenant, harness.cost_usd, harness.policy_version, harness.stop_reason). Default roop se raw prompts spans mein mat daalo; telemetry tak aksar audit store se zyaada logon ki pahunch hoti hai.

What we learnedHumne kya seekha

  1. Trace every run: each model call and tool call is a span with tokens, cost and time.
  2. Roll the spans up: a few calls can cause most of the cost or the slowest waits.
  3. Watch behaviour signals for drift, not only errors.
  4. Have a kill switch, a rollback, and a habit of turning incidents into eval cases.
  1. Har run trace karo: har model call aur tool call ek span hai jisme tokens, kharch aur samay hai.
  2. Spans jodo: thodi si calls zyaadatar kharch ya sabse lamba intezaar paida kar sakti hain.
  3. Drift ke liye sirf errors nahi, behaviour signals dekho.
  4. Kill switch, rollback, aur incidents ko eval cases banaane ki aadat rakho.
