Haron at HomeGhar ka Haron

The bank says: "Our data never leaves our building." So Acme must run a Haron of its own, an open-weights model like Llama or Qwen, on the bank's own GPUs. Now the team owns everything a cloud provider used to hide: how much GPU memory the model needs, how many customers one server can serve, and what happens at 9 a.m. when everyone logs in.

Bank kehta hai: "Hamara data hamari building se bahar nahi jaata." Isliye Acme ko apna khud ka Haron chalaana padega, Llama ya Qwen jaisa open-weights model, bank ke apne GPUs par. Ab woh sab team ki zimmedaari hai jo cloud provider chhupa leta tha: model ko kitni GPU memory chahiye, ek server kitne customers sambhaal sakta hai, aur subah 9 baje kya hota hai jab sab login karte hain.

1

How many GPUs?Kitne GPUs?

A GPU has a fixed amount of memory (80 GB on common data-centre cards). Three things must fit: the model's weights, the sticky notes (KV cache, Chapter 1) for every user being served at once, and some working space. Here are real calculations from this chapter's lab.

GPU ki memory tay hoti hai (aam data-centre cards par 80 GB). Teen cheezein fit honi chahiye: model ke weights, ek saath serve ho rahe har user ke sticky notes (KV cache, Chapter 1), aur kuch kaam ki jagah. Yeh is chapter ke lab ke asli hisaab hain.

RememberYaad rakho

Quantisation stores each number with fewer bits: bf16 (2 bytes) → fp8 (1 byte) → int4 (half a byte). It halves or quarters memory and often speeds things up, with a small quality loss that you must measure on your own evals, especially for maths, code and Indian languages. Long contexts make the KV cache, not the weights, the biggest cost.

Quantisation har number ko kam bits mein rakhta hai: bf16 (2 bytes) → fp8 (1 byte) → int4 (aadha byte). Memory aadhi ya chauthaai ho jaati hai aur aksar speed badhti hai, thode quality nuksaan ke saath jise apne evals par naapna zaroori hai, khaaskar maths, code aur Indian bhashaon ke liye. Lambe context mein weights nahi, KV cache sabse bada kharch banta hai.

2

Don't wait for the slowestSabse dheeme ka intezaar mat karo

A GPU is fastest when it serves many requests together (a batch). Old servers formed a batch, waited until every request in it finished, then started the next batch: like a bus that waits until the last passenger reaches their stop before picking anyone up. Modern servers such as vLLM use continuous batching: the moment one request finishes, a new one takes its seat.

GPU sabse tez tab hota hai jab woh kai requests ek saath serve kare (batch). Purane servers batch banaate, har request khatam hone tak rukte, phir agla batch shuru karte: jaise bus jo aakhri sawaari ke utarne tak kisi ko nahi chadhaati. vLLM jaise modern servers continuous batching use karte hain: jaise hi ek request khatam, nayi uski seat le leti hai.

AI behaviour

An open model is not a drop-in for a frontier modelOpen model frontier model ki seedhi jagah nahi le sakta

The same agent that works well on a frontier API may call tools less reliably, lose the format more often, or reason worse on long tasks with a smaller open model. Give the on-prem model simpler, more structured jobs (extraction, classification, summarising one document), shorter contexts and stricter output schemas, and run the full eval suite before switching any route.

Jo agent frontier API par achha chalta hai, woh chhote open model ke saath tools kam bharose se call kar sakta hai, format zyaada todta hai, ya lambe kaamon mein kamzor sochta hai. On-prem model ko seedhe, structured kaam do (extraction, classification, ek document ka summary), chhote contexts aur sakht output schemas, aur kisi bhi route ko badalne se pehle poora eval suite chalao.

Enterprise

The true cost of "free" weights"Muft" weights ki asli keemat

Open weights cost nothing to download, but GPUs, power, cooling, on-call engineers, security patching, model upgrades and idle capacity at night are all yours. Compute an internal price per million tokens = (all monthly costs) ÷ (tokens actually served), put it in the price table (Chapter 2), and compare honestly with the API. Self-hosting usually wins on data control and steady high volume, rarely on small or spiky workloads.

Open weights download karna muft hai, par GPUs, bijli, cooling, on-call engineers, security patching, model upgrades aur raat ki khaali capacity sab aapki hai. Andaruni daam per million tokens = (mahine ke saare kharch) ÷ (sach mein serve hue tokens) nikaalo, price table (Chapter 2) mein daalo, aur API se imaandaari se compare karo. Self-hosting aksar data control aur lagaataar bade volume par jeetta hai, chhote ya uchhalte workloads par kam.

What we learnedHumne kya seekha

  1. At home I need memory for my weights, my sticky notes for every user, and some room to work.
  2. Smaller numbers (fp8, int4) save memory; test that I'm still good enough.
  3. Continuous batching keeps the GPU busy.
  4. Keep sensitive work at home, send the rest to the cloud, and compare costs honestly.
  1. Ghar par mujhe weights, har user ke sticky notes, aur kaam ki jagah ke liye memory chahiye.
  2. Chhote numbers (fp8, int4) memory bachaate hain; test karo ki main ab bhi kaafi achha hoon.
  3. Continuous batching GPU ko vyast rakhta hai.
  4. Sensitive kaam ghar par, baaki cloud par, aur kharch imaandaari se compare karo.
