The Manager's LoopManager ka Loop

Haron can only answer once. To do a job, like booking a flight, someone must keep asking: "What next?", run what Haron asks for, show it the result, and decide when to stop. That someone is the Manager, and the pattern is called the agent loop. It is the heart of every agent harness, and it is surprisingly small.

Haron sirf ek baar jawab de sakta hai. Koi kaam karne ke liye, jaise flight book karna, kisi ko baar-baar poochna padta hai: "Ab kya?", Haron jo maange woh chalaana padta hai, result dikhaana padta hai, aur tay karna padta hai ki kab rukna hai. Woh koi hai Manager, aur is pattern ko agent loop kehte hain. Yeh har agent harness ka dil hai, aur hairat ki baat hai ki bahut chhota hai.

2

Six doors out of the loopLoop se bahar ke chhe darwaaze

A loop with only one exit ("Haron says it's done") will one day run forever and burn money. A good Manager has six doors, and every run must leave through one of them, with the reason written down.

Jis loop ka sirf ek darwaaza ho ("Haron bole ho gaya"), woh ek din hamesha chalta rahega aur paisa jalaayega. Achhe Manager ke chhe darwaaze hote hain, aur har run inme se kisi ek se nikalta hai, wajah likhkar.

AI behaviour

Agents declare victory early, and agents wanderAgents jaldi jeet ka elaan karte hain, aur bhatakte bhi hain

Two opposite failures. Sometimes Haron stops at the first plausible result ("Booked!" when the booking tool actually failed). Sometimes it keeps exploring, re-reading files and re-running searches, long after it has enough. The first is fixed by checking the outcome with code before accepting "done"; the second by step and token limits plus the repeat detector.

Do ulti galtiyaan. Kabhi Haron pehle vishwasniya result par ruk jaata hai ("Book ho gaya!" jabki booking tool fail hua tha). Kabhi woh khojta rehta hai, files dobara padhta hai, search dobara chalaata hai, jabki kaafi jaankari mil chuki hai. Pehli ka ilaaj: "done" maanne se pehle result code se check karo; doosri ka: step aur token limits aur repeat detector.

3

Three ways to run the loopLoop chalaane ke teen tareeke

Harness note

Start with the simplest loop that worksSabse seedhe loop se shuru karo jo chal jaaye

Most production agents are plain ReAct loops with good tools, a clear system prompt and strong stop rules. Add a planner when tasks are long and steps are predictable; add reflection when quality matters more than latency and you have a way to critique (tests, a rubric). Each extra pattern adds cost and new ways to fail.

Zyaadatar production agents seedhe ReAct loops hain, achhe tools, saaf system prompt aur majboot rukne ke niyam ke saath. Planner tab jodo jab kaam lambe hon aur steps pehle se pata hon; reflection tab jodo jab quality latency se zyaada zaroori ho aur critique ka tareeka ho (tests, rubric). Har extra pattern kharch aur fail hone ke naye raaste jodta hai.

Enterprise

Loops crash; bookings must not happen twiceLoops crash hote hain; booking do baar nahi honi chahiye

In production, a server can restart mid-run. Save the transcript after every step so the run can resume, and give every write action an idempotency key (for example a hash of run ID + step), so retrying "book_flight" never books two seats. Workflow engines like Temporal are often used to make agent runs durable.

Production mein server run ke beech restart ho sakta hai. Har step ke baad transcript save karo taaki run wahin se shuru ho sake, aur har write action ko idempotency key do (jaise run ID + step ka hash), taaki "book_flight" dobara chalne par do seat book na ho. Agent runs ko tikaau banane ke liye aksar Temporal jaise workflow engines use hote hain.

for step in range(1, cfg.max_steps + 1):
    if cfg.token_budget is not None and usage.total >= cfg.token_budget:
        return result("budget", step - 1)
    resp = self.provider.complete(model=cfg.model, system=cfg.system,
                                  messages=self.context.prepare(messages), tools=self.tools.specs())
    usage = usage + resp.usage
    messages.append(Message("assistant", resp.text, tool_calls=resp.tool_calls))
    if resp.stop_reason in ("refusal", "max_tokens") and not resp.tool_calls:
        return result(resp.stop_reason, step)
    if not resp.tool_calls:
        return result("done", step)
    for call in resp.tool_calls:
        if repeated(call) >= cfg.repeat_limit:
            return result("stuck", step)
        deny = first Deny from hooks.emit("pre_tool", call=call)
        content, err = (f"Blocked by policy: {deny.reason}", True) if deny \
                       else self.tools.execute(call, cfg.permission_mode, self.approver)
        messages.append(Message("tool", content, tool_call_id=call.id, is_error=err))
return result("max_steps", cfg.max_steps)

What we learnedHumne kya seekha

  1. I think, the team acts, I see the result, and we repeat.
  2. Every run must leave by a named door: done, max steps, budget, stuck, refusal or max tokens.
  3. Don't trust my "done"; check the result.
  4. Keep the loop simple; save progress; never do a write action twice.
  1. Main sochta hoon, team karti hai, main result dekhta hoon, aur phir se.
  2. Har run naam wale darwaaze se nikle: done, max steps, budget, stuck, refusal ya max tokens.
  3. Mere "done" par bharosa mat karo; result check karo.
  4. Loop seedha rakho; progress save karo; write action kabhi do baar mat karo.
